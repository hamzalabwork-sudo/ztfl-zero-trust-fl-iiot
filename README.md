# Zero-Trust Federated Intrusion Detection for IIoT: Poisoning as Privilege Escalation

Code, experiment record and result summaries for a study of **model poisoning in federated,
learning-driven Zero-Trust access control for the Industrial Internet of Things (IIoT)**.

In such a system the intrusion detector that authorizes devices is itself trained, by federated
learning, by the gateways it polices. A participant that poisons the detector so that its own traffic
is scored benign does not merely lower accuracy: it **escalates its own privilege** at the gateway.
This repository measures that failure in access-control terms and closes the loop the Zero-Trust way:

| | Contribution | Where in the code |
|---|---|---|
| **C1** | Poisoning measured as privilege escalation (wrongful-grant rate, time-to-isolation, false re-authorization, lateral reach) across a 1,350-run attack x defense study | `src/stage3.py`, `src/poison.py` |
| **C2** | Continuous device authorization as sequential change detection (CUSUM + mixture SPRT) with a provable false-alarm bound (Lorden) and a rare-type-robust evidence model | `src/closed_loop.py`, `stage4/common.py` |
| **C3** | Federated clients as Zero-Trust subjects: a statistical per-type deployment gate, counterfactual client attribution, revocation and rollback, recorded on a hash-chained / EVM provenance ledger | `src/canary.py`, `src/client_trust.py`, `src/ledger.py`, `contracts/` |
| | End-to-end validation on an emulated Docker testbed (real MQTT identity, timing, enforcement) | `stage4/` |

Everything needed to **reproduce or check any number** is described below, from a ten-minute sanity
check to a full re-run. The complete experiment log, including negative and superseded results, is in
[`EXPERIMENTS.md`](EXPERIMENTS.md).

---

## 1. Repository layout

```
src/                 all simulation code (datasets, detectors, FL, attacks, gates, attribution,
                     closed-loop gateway, ledger, summaries)
stage4/              emulated device testbed (Docker: MQTT broker, device containers, gateway, EVM)
contracts/           Solidity provenance contract (+ compiled artifact used by the EVM ledger)
scripts/             the batch queues used to run the experiment matrices
results/             result SUMMARIES (markdown/CSV) for every experiment, plus small evidence files
stage4/results/      testbed outcomes (one JSON per session) and their summary
data/                where the three public datasets go (not redistributed; see data/README.md)
EXPERIMENTS.md       the experiment record: question, configuration, results, decision for E0-E10, R1-R3
requirements*.txt    pinned Python environment
```

Per-run result files (several thousand JSON files, ~320 MB) are not stored in git; every summary in
`results/` is regenerated from them by the `src/summarize*.py` scripts, and every per-run file is
regenerated by re-running the experiment (Section 4).

## 2. Setup

**Environment used for all reported results:** Linux, Python 3.10.12, one NVIDIA RTX 3090 per run,
`torch 2.14.1`. The testbed (Stage 4) ran under Docker Desktop with the images described in
`stage4/README.md`.

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt                         # simulation (CPU wheels work; CUDA optional)
pip install -r requirements-testbed.txt                 # only for the EVM ledger / testbed tools
```

**Datasets.** The three public datasets are not redistributed. Download them as described in
[`data/README.md`](data/README.md), place the CSV files in `data/raw/`, and verify that you have
exactly the files that were used:

```bash
python scripts/check_data.py          # prints OK / MISMATCH / MISSING for each file (SHA-256)
```

The first run of any experiment cleans and splits a dataset once and caches it in `data/cache/`
(deterministic per seed).

## 3. Three levels of verification

### Level 1 - read the evidence (minutes, no data, no GPU)
Every headline number in the study can be traced to a file shipped here:

| Claim | Expected value | File to check |
|---|---|---|
| Detectors are statistically tied after cleaning (federated MLP, macro-F1) | Edge 0.9982, Forge 0.9918, WUSTL 0.9993 | `results/fed/a0.5_k10/summary.md` |
| C1: undefended last-round FedAvg backdoor success, m = 3 | 97.7 / 100 / 99.5 % | `results/poison/summary.md` |
| C2: false isolation of `cusum_sprt_mix` with Lorden's threshold (budget 1 %) | 0.00-0.03 % mean per dataset and rate; worst seed 0.12 % (E5c in `EXPERIMENTS.md`) | `results/closed_loop/monotone_lorden/summary.md` |
| C2: rare Forge attack type isolated with balanced evidence | 0 % -> 100 % of devices | `results/closed_loop/e5e_summary.md` |
| C3: full-system backdoor excess, attack from round 1 (Edge / Forge / WUSTL) | 0.3 / 0.9 / 13.0 pp (column `canary_stat_slo / trust`) | `results/e9/summary.md` |
| C3: honest clients revoked in clean FedAvg runs (attack `none`, column `revoked_false`) | 0 on every dataset (0 of 360 client-runs) | `results/e9/summary.md` |
| Testbed: compromised devices isolated; per-event cost on one core | 100 %; 0.375 ms | `stage4/results/summary.md` |
| Evaluation fidelity: backdoor success on unseen test rows vs. all rows | unchanged (e.g. Edge 0.979 all / 1.000 unseen) | `results/r1b/*/s*.json` |

`EXPERIMENTS.md` gives, for each experiment, the exact configuration, the code version and the
interpretation, and keeps failed and superseded variants rather than overwriting them.

### Level 2 - re-run a cell yourself (under an hour, Edge-IIoTset only, CPU is enough)
Edge-IIoTset is freely downloadable, so the following checks need only that one file:

```bash
# (a) evaluation fidelity: backdoor success on all vs. unseen target rows, seed 42
python src/r1b.py --datasets edgeiiot --seeds 42
#   expected: bd all/unseen=0.979/1.000   (reproduced identically on CPU and GPU)

# (b) the full system against a backdoor present from round 1 (one seed, one cell)
python src/e9.py --variant trust --datasets edgeiiot --attacks backdoor --aggregators fedavg \
                 --malicious 3 --onsets 1 --seeds 43
#   expected: bad=[0, 3, 7]  revoked=[0, 3, 7]   (all three attackers revoked, no honest client)
#             deployed-model backdoor success ~0.016   (stored GPU value 0.0162)
```

Outputs are written under `results/` and are skipped if they already exist; delete the output file
to force a re-run.

### Level 3 - full reproduction (GPU, days)
Run the commands in Section 4 in order. The batch queues in `scripts/` are the ones that produced the
reported results; they assume a virtual environment at `.venv/` and two GPUs (`CUDA_VISIBLE_DEVICES`
0 and 1). Adjust both to your machine. All queues are resumable: finished runs are skipped.

## 5. Determinism and provenance

- **Seeds.** Seed 42 is the design/calibration seed; seeds 43-46 are evaluation seeds reported
  separately, so no design choice was tuned on the evaluation seeds.
- **Deterministic aggregation.** Clients are aggregated in a fixed order and all randomness is seeded,
  so a seed reproduces a run exactly on the same platform. Across CPU and GPU, floating-point results
  can differ in the last decimals while discrete outcomes (which clients are revoked, which rounds are
  rejected) are unchanged.
- **Code version.** Every per-run result records `code_version`, a hash of the raw bytes of all
  `src/*.py` files on the machine that ran it (`src/train_central.py::code_version`). It groups runs
  made with the same code; it is not a checksum of this repository, for two reasons. First, the code
  grew stage by stage, so earlier experiments carry earlier hashes; later changes added options and
  modules while keeping existing defaults unchanged. Second, the study used a Windows workstation and a
  Linux server, so line endings differed between machines, and the hash sees bytes, not content.
- **What the published code is.** Line endings aside, `src/` here is file-for-file identical to the
  code that produced the latest stored runs (R1a, R1b, R2), plus two read-only summary scripts
  (`summarize_e9.py`, `summarize_e10.py`) and the on-chain audit added for E10-chain
  (`EvmLedger.audit()` in `src/ledger.py`; it only extends the EVM backend, so the in-memory ledger
  used by E5-E9 is unchanged), extended for E12 with locally signed zero-gas transactions for public
  networks (`EvmLedger(..., keys=...)`; without keys the anvil path is unchanged and gives identical gas).
  With that code, re-running a stored E9 configuration
  reproduced the stored result bit-for-bit on the same GPU. This repository's `src/` hashes to
  `473b4cbb2c5b`
  (`python -c "import sys; sys.path.insert(0,'src'); from train_central import code_version; print(code_version())"`),
  and `.gitattributes` fixes LF line endings so that hash is the same on every platform.
- **Data.** `scripts/check_data.py` pins the exact raw files by SHA-256; cleaning rules are versioned
  by `PREP_VERSION` in `src/datasets.py`.
- **Ledger integrity.** The provenance ledger is a hash chain; promotion verdicts depend only on
  integer canary counts, so any verdict can be recomputed from the ledger record. On the EVM backend,
  every run ends with an audit that rebuilds each record from the contract's events alone and compares
  it with the local hash chain (`chain.audit` in each `*_evm.json`), and `chain.failed` counts reverted
  transactions; both should read 0 failures and a full match.

## 6. Compute

The full study is several thousand federated runs (each 30 rounds; from about 20 s on Edge/WUSTL to
about 70 s on Forge on an RTX 3090) plus the closed-loop and testbed experiments. Single cells
(Level 2) run in minutes on a CPU.
